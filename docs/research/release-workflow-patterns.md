# Release-workflow patterns in mature Rust projects

- Date: 2026-04-28
- Author: Jace Babin (w/ Claude Code)
- Scope: Survey how mature Rust open-source projects trigger and validate their release workflows on GitHub Actions, with focus on **how they validate release-infra changes pre-merge without burning a full multi-target build matrix on every PR**. Drives a pending ADR on linesmith's release-trigger surface.

## Question

linesmith's `.github/workflows/release.yml` is autogenerated by [`cargo-dist`](https://opensource.axo.dev/cargo-dist/) and currently fires on tag-push + `workflow_dispatch` (manual dry-run). Each run is a 7-target build matrix at ~10 min × 7 runners. Should we add a `pull_request` trigger (path-filtered to release-infra files: `release.yml`, `dist-workspace.toml`, `release-plz.toml`, `Cargo.toml`) so changes to release plumbing get exercised pre-merge, and if so, what mode keeps compute proportional to the validation goal?

## Sequencing mechanisms in production

**`workflow_run: types: [completed]`.** Used by `rust-lang/rust-bindgen`'s `publish.yml` to wait for the `Release` workflow before invoking `cargo publish`:

```yaml
on:
  workflow_run:
    workflows:
      - Release
    types:
      - completed
jobs:
  cargo-publish:
    if: ${{ !github.event.pull_request && (github.event.workflow_run.conclusion == 'success') && (github.event.workflow.name == 'Release') }}
```

`rust-lang/rust-clippy` and `rust-lang/team` use the same pattern (the Clippy `lintcheck_summary` workflow has an inline comment that captures the security caveat: _"This action must not checkout/run code from the originating workflow_run or directly interpolate ${{}} untrusted fields into code"_). The known security caveat — workflow*run runs with the **default-branch's workflow definition**, not the PR head's — is exactly why none of the surveyed projects use `workflow_run` to validate release-workflow \_changes* themselves: the PR's modified `release.yml` is not the file that executes.

**Reusable workflows via `workflow_call`.** `astral-sh/uv` uses this for its `check-release.yml`:

```yaml
on:
  workflow_call:
jobs:
  dist-plan:
    name: 'dist plan'
    runs-on: ubuntu-latest
    steps:
      - run: dist plan --output-format=json > plan-dist-manifest.json
```

A reusable workflow can be called from another workflow's `jobs.<id>.uses:` plus `needs:`, giving a true sequencing chain inside a single dispatch. uv composes its release matrix from `build-release-binaries.yml`, `build-docker.yml`, etc., all of which are `workflow_call` files.

**`lewagon/wait-on-check-action` (polling action).** Searched explicitly. No mature Rust project in this survey uses it; the `gh search code` results for `wait-on-check-action` against Rust repos surface only template/example/scrape repos, no production Rust release pipelines. This appears to be a non-idiomatic choice in the Rust ecosystem.

**Native `needs:` (intra-workflow).** Universal inside cargo-dist's generated `release.yml` itself: every job declares `needs: [plan, ...]` so the build matrix is gated on `plan`. But native `needs:` cannot reach across workflow files.

**Branch-protection required-checks.** Gates _merge_, not run-order. None of the surveyed projects describe using it for sequencing release builds.

## cargo-dist + release-plz topology

cargo-dist's own `release.yml` exposes a config knob for exactly the question linesmith is asking:

```toml
# axodotdev/cargo-dist's dist-workspace.toml
pr-run-mode = "plan"
```

cargo-dist's [book reference](https://opensource.axo.dev/cargo-dist/book/reference/config.html#pr-run-mode) documents the three values (the knob was introduced in v0.3.0 alongside `allow-dirty = ["ci"]`):

- **`skip`**: do nothing on `pull_request`. (linesmith's current setting per `dist-workspace.toml`.)
- **`plan`** (default for cargo-dist itself): run only the cheap `dist plan` job on PRs, which validates `dist-workspace.toml` and emits `plan-dist-manifest.json`. **No build matrix.**
- **`upload`**: run plan + the full build matrix, attach artifacts to the workflow's Summary as `artifacts.zip`, but skip publish/announce. cargo-dist's v0.3.0 changelog calls it out: _"this upload mode is great for making sure the Windows build works even if you only have a Linux machine [...] although you should probably only keep it on temporarily, as it's very slow and wasteful to build all those shippable artifacts for every PR."_

cargo-dist's `release.yml` also documents that the `workflow_dispatch` `dry-run` tag input (the same pattern linesmith uses) is _"taken to have the same meaning as `pr-run-mode = upload`: run the plan and build steps, but not the publish or announce ones."_ The two paths are functionally equivalent — only the trigger differs.

**Repos using both cargo-dist and release-plz.** `gh search code "release-plz" "cargo-dist"` returns mostly third-party / template repositories; the canonical authors don't co-deploy the two tools (cargo-dist's repo doesn't use release-plz, and release-plz's repo doesn't use cargo-dist — release-plz uses `taiki-e/upload-rust-binary-action` on `release: published`). The pattern in third-party consumers (`timcogan/perspecta`, several others) is consistent:

```yaml
# perspecta/.github/workflows/release.yml
on:
  pull_request:
  workflow_dispatch:
  push:
    branches: [main, master]
    paths:
      - Cargo.toml
      - dist-workspace.toml
      - .github/workflows/release.yml
```

The two tools occupy non-overlapping roles: release-plz prepares versioning + crates.io publishes (runs on `push: main`); cargo-dist builds + attaches binaries to GH Releases (runs on `push: tags` or `release: published`). Neither tool sequences against the other in any of the workflows surveyed; they just both exist in the `.github/workflows/` directory and fire on different triggers.

## Two-tier alternative

A "PRs run cheap validation, tags run full builds" split is **the documented default** for cargo-dist (`pr-run-mode = "plan"`) and is what cargo-dist itself ships. The pattern is also what `astral-sh/uv` enforces via `check-release.yml` as a reusable workflow that calls `dist plan` and nothing else.

`gh search code "dist plan" language:yaml` returns ~30 results across Rust repos — most are workflows that invoke `dist plan` as the first job inside a larger autogenerated `release.yml` (which is what cargo-dist's template does). A standalone "cheap-validation" workflow that _only_ runs `dist plan` is rarer; uv's `check-release.yml` is the cleanest example. No project in the survey runs `release-plz update --check` as a standalone PR validation step (`gh search code` for that string returns zero hits).

## Patterns observed

1. **Tag-push / dispatch-only is dominant for binary release pipelines.** Every project that ships binaries (clap, uv, rust-analyzer, release-plz, rust-bindgen) restricts the heavy multi-target build to either tag-push, `release: published`, scheduled cron, or `workflow_dispatch`. None of them use a vanilla `pull_request:` trigger that runs the full matrix every time.

2. **Cargo-dist consumers default to "plan-only on PR".**
   - **Plan-only on PR** (cargo-dist itself, default): `pull_request:` trigger, `pr-run-mode = "plan"`, build matrix gated by `if: needs.plan.outputs.publishing == 'true' || ...artifacts_matrix.include != null`. PR runs cost ~1 min, exercise the modified workflow file.
   - No surveyed cargo-dist consumer ships a **path-filtered `pull_request:` trigger**. Round 3 §1 confirmed that the cargo-dist Jinja template emits a bare `pull_request:` with no native `paths:` knob, and `timcogan/perspecta`'s hand-edited path filter applies to its `push:` trigger only — its `pull_request:` is template-default-unfiltered. The corpus has no precedent for path-filtering the PR trigger specifically.

3. **`workflow_dispatch` dry-run is the mature compromise.** uv's `release-gate` environment (2-factor approval) plus dispatch-only triggering is a defensible posture for projects that _don't want_ PR-side build runs. cargo-dist's own changelog notes that `workflow_dispatch` with a `dry-run` tag is functionally the same as `pr-run-mode = "upload"` on a PR.

4. **`workflow_run` is the wrong tool for release-infra validation.** Even the projects that use `workflow_run` (`rust-bindgen`, `rust-clippy`'s lintcheck) gate publish/announce _after_ a CI run, not as a PR validation step. The "default-branch workflow definition" semantics make it actively unsuitable for testing PR-modified workflow YAML.

5. **Path filtering on release-workflow `pull_request:` triggers is unblazed.** None of tokio/serde/clap/uv/cargo-dist/release-plz/ratatui put a path filter on their _release_ workflow PR trigger; perspecta does path-filter, but only on `push:`, not `pull_request:` (Round 3 §1). tokio's `pr-audit.yml` does path-filter on `**/Cargo.toml` for cargo-deny, which is the closest analogue at a different scope: cheap workflow + path filter to scope what fires it.

6. **`lewagon/wait-on-check-action` is non-idiomatic in this corpus.** Zero hits in mature Rust release pipelines surveyed. The Rust ecosystem appears to favor `needs:` (intra-workflow), `workflow_call` (compose), or `workflow_run` (post-success chaining) over polling actions.

## What this leaves unresolved

Round 1 surfaced five open questions; Rounds 2 and 3 closed most of them. The remaining unresolved items are narrower than the original framing.

- **Empirical frequency of release-infra-induced target-specific failures.** Round 2 §1 confirmed that `plan` mode would NOT have caught the v0.1.1 cross-compile blocker — that's the toolchain-bug class, in `plan`'s blind spot, with `upload` documented as the right fix. What's still unresolved is _how often_ that class fires for linesmith specifically. v0.1.1 is one data point; whether the rate justifies the upload-mode-on-every-PR cost (or the path-filtered hand-edit alternative) is a judgment call the survey can't make.

- **Trigger semantics for `release.yml` modifications specifically.** None of the surveyed projects publish a writeup of _why_ they chose plan vs. upload vs. dispatch-only. uv's choice of dispatch-only-with-environment-gate is plausibly motivated by their high release cadence and security posture (release-gate is a 2-factor approval) — but that's inference, not stated rationale.

- **Path-filter precision.** linesmith's prospective filter (`release.yml`, `dist-workspace.toml`, `Cargo.toml`, `crates/*/Cargo.toml`, `Cargo.lock`) overlaps with normal-PR concerns: a routine dependency bump touches `Cargo.toml` + `Cargo.lock` and would fire the heavy workflow. tokio handles this for `audit.yml` by accepting the over-trigger (cargo-deny is cheap). For a 7-target matrix the over-trigger is more expensive but bounded (every dep PR ≈ one matrix run). No surveyed peer has a path-filtered `pull_request:` trigger to draw from for the precision-vs-coverage tradeoff.

### Resolved by Round 2

- ~~**Plan-only's blind spot for `release-plz.toml`**~~ → confirmed (Round 2 §2): release-plz has no PR-time check mode (`Update | ReleasePr | Release | GenerateCompletions | CheckUpdates | GenerateSchema | Init | SetVersion`, none with `--check`), so the gap is real and unblazed in the surveyed corpus. The implementation question (custom validator vs. accept the gap) lives in the ADR follow-up, not in further research.
- ~~**Plan-only catches dist-workspace.toml syntax but not target-specific build failures**~~ → confirmed (Round 2 §1): `do_manifest` never invokes `cargo build` / `rustup` / `xwin` / `zigbuild`; cargo-dist's troubleshooting page recommends `upload` for exactly this class.

### Resolved by Round 3

- ~~**What `pr-run-mode = "skip"` actually loses**~~ → answered (Round 3 §1): flipping to `upload` would emit a bare `pull_request:` (no native `paths:` filter, no `pr-run-paths` knob exists). Path filtering on a PR trigger is strictly hand-edit territory regardless of mode.
- ~~**Hand-edit survival across cargo-dist regen**~~ (implicit Round 1 worry, made explicit in Round 3 §2) → answered: under `allow-dirty = ["ci"]`, `dist init` skips the file entirely (`should_run` returns `false` and the write loop short-circuits). Hand-edits survive forever; template fixes also stop reaching the file until the un-allow-dirty cycle runs manually.

## Round 2 follow-ups

Three open questions from round 1 — what `dist plan` actually catches, whether `release-plz` exposes a check mode, and whether public-repo Actions minutes are truly unconstrained — got definitive answers via cargo-dist + release-plz source and the GitHub billing/limits docs.

### 1. `dist plan` validates config and graph topology, never toolchains

**Question.** Would `dist plan` have caught the `aarch64-pc-windows-msvc` cross-compile blocker (commit `c219174`, "cargo-xwin emits MSVC-style include paths as `/imsvc /path`... ring's C build hits this consistently and fails during cross-compile") that broke linesmith's v0.1.1 release?

**Evidence.** `cargo-dist/src/main.rs` defines `cmd_plan` as an alias for `dist manifest --artifacts=all --no-local-paths`; both call `generate_manifest → do_manifest`. The full body of `do_manifest` ([`cargo-dist/src/lib.rs:189`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/src/lib.rs)):

```rust
pub fn do_manifest(cfg: &Config) -> DistResult<DistManifest> {
    check_integrity(cfg)?;
    let (_dist, manifest) = gather_work(cfg)?;
    Ok(manifest)
}
```

`check_integrity` is documented in-source as "currently equivalent to `dist generate --check`" — it re-generates the CI YAML and installer scripts from config and diffs them against on-disk copies, catching drift between `dist-workspace.toml` and a hand-edited `release.yml`. `gather_work` resolves the dependency graph and decides which `BuildStep`s would run. Neither calls `run_build_step`, `rustup_toolchain`, `cargo build`, `xwin`, `zigbuild`, or any compiler. The cargo-dist book confirms the operational framing: _"By default, dist will run the plan step on every pull request but won't perform a full release build"_ ([book/src/ci/customizing.md:254](https://github.com/axodotdev/cargo-dist/blob/main/book/src/ci/customizing.md)). And the troubleshooting page explicitly recommends `pr-run-mode = "upload"` for the cross-compile case: _"If the issue appears to be exclusive to dist CI, we recommend opening a PR against your project with `pr-run-mode = \"upload\"` temporarily enabled"_ ([book/src/troubleshooting.md](https://github.com/axodotdev/cargo-dist/blob/main/book/src/troubleshooting.md)).

**Answer.** No — `plan` would not have caught the v0.1.1 blocker. `plan` catches: TOML syntax errors, unknown target triples (rejected at `target_triple.parse()`), tag/version incoherence, and stale generated CI files. It does **not** catch: missing/broken cross-compile toolchains, ring/cc-rs/xwin interaction bugs, OOM, OS-specific link errors, or dependency build failures. The v0.1.1 failure was strictly a build-time toolchain issue and lives entirely in the upload-mode-only blind spot.

### 2. `release-plz` has no PR-time config-validation mode

**Question.** Does `release-plz` expose a check / dry-run / validate mode usable as a PR-time pre-flight against `release-plz.toml`?

**Evidence.** From [`crates/release_plz/src/args/mod.rs`](https://github.com/release-plz/release-plz/blob/main/crates/release_plz/src/args/mod.rs), the full subcommand list is `Update | ReleasePr | Release | GenerateCompletions | CheckUpdates | GenerateSchema | Init | SetVersion`. Per-subcommand findings:

- `release-plz update` is doc-stringed as _"Update your project locally, without opening a PR"_ ([`update.rs:23`](https://github.com/release-plz/release-plz/blob/main/crates/release_plz/src/args/update.rs)). It mutates `Cargo.toml` and changelogs in the working tree; closest thing to a dry run, but it modifies files and doesn't have a `--check` flag.
- `release-plz release` has `pub dry_run: bool` doc-stringed _"Perform all checks without uploading"_ ([`release.rs:38`](https://github.com/release-plz/release-plz/blob/main/crates/release_plz/src/args/release.rs)) — but that's the publish step, not the PR step, and it requires registry tokens.
- `release-plz release-pr` flattens `Update` and adds output formatting; has no `--dry-run` flag of its own ([`release_pr.rs`](https://github.com/release-plz/release-plz/blob/main/crates/release_plz/src/args/release_pr.rs)).
- `release-plz generate-schema` writes `.schema/latest.json` for IDE completion via `schemars::schema_for!(config::Config)` ([`generate_schema.rs:21`](https://github.com/release-plz/release-plz/blob/main/crates/release_plz/src/generate_schema.rs)) — useful for editor-time validation but not a CLI pre-flight. Comment in source: _"meant to be used on `SchemaStore` for IDE completion"_.
- No `Check`, `Validate`, `Lint`, or `--check` exists anywhere in the subcommand enum.

release-plz's own `.github/workflows/ci.yml` runs `cargo-semver-checks`, `cargo test`, `rustfmt`, `clippy`, `cargo doc` on PRs — and notably **does not** invoke `release-plz` itself for any kind of self-check. That's a strong signal: even the project's own maintainers don't have a canonical PR-time validation step.

**Answer.** No PR-time check mode exists. The closest pre-flight is JSON-schema validation in an editor (via `release-plz generate-schema`); the closest CLI dry-run is `release-plz update`, which mutates the working tree and would need `--allow-dirty` plus a follow-up `git diff --exit-code` to be useful in CI. Round 1's "unblazed-path" finding stands — confirmed.

### 3. Public-repo Actions minutes are unlimited; the relevant cap is concurrency

**Question.** Confirm public-repo Actions minutes are unlimited, and surface any caveats.

**Evidence.** From [GitHub's billing docs](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions): _"GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners."_ macOS standard runners are ~10× the price of Linux 2-core ($0.062 vs $0.006/min) — but that pricing is **moot for public repos using standard runners**. Larger runners are the exception: per the [larger-runners docs](https://docs.github.com/en/actions/concepts/runners/about-larger-runners), they always bill at the per-minute rate even on public repos. linesmith's `release.yml` uses standard `macos-13`, `windows-2022`, `ubuntu-22.04` runners, not larger runners.

The non-minutes caps from [Actions limits docs](https://docs.github.com/en/actions/reference/limits): per-job 6h ceiling, per-workflow 35-day ceiling, **GitHub Free plan: 20 concurrent jobs total across all repositories** in the billing entity. Artifact storage on GitHub Free is 500 MB shared with Packages.

**Answer.** Confirmed — minutes are unlimited on public repos with standard runners. The real ceiling is the Free-plan 20-concurrent-job cap, which applies account-wide; a 7-target release fan-out would consume 7 of 20 slots if it raced with other CI. The minutes-cost framing is the wrong concern; the design decision should be driven by signal quality, feedback latency, and required-check noise.

### Bonus: cargo-dist has a `dry-run` workflow_dispatch input that's equivalent to `pr-run-mode = "upload"` — without the PR

The cargo-dist v0.8.0 changelog notes the `workflow_dispatch` form's default tag input is _"taken to have the same meaning as `pr-run-mode = upload`: run the plan and build steps, but not the publish or announce ones"_. Round 1 cited this in passing, but the operational implication is sharper than it reads: a dispatch-driven dry-run gives the _full upload-mode signal_ (build matrix exercises every target, artifacts uploaded to the run summary) **on demand, without needing a PR or a `pr-run-mode` change**. For linesmith's actual failure mode — rare cross-compile breakage on infra changes — a manually-invoked dispatch with `dry-run` is functionally equivalent to upload-mode-on-PR, just human-triggered. This is what linesmith already has; whether the friction of "I have to remember to dispatch it" is worth the cleanliness of "no PR-time matrix" is a UX question, not a capability question.

## Round 3: pr-run-mode = "upload" implementation specifics

Three implementation-blocking questions about flipping `pr-run-mode` from `skip` to `upload` — paths-filter behavior, `dist init` regen semantics under `allow-dirty`, and fork-PR attestation handling — got definitive answers from the cargo-dist Jinja template and source.

### 1. The generated `pull_request:` trigger has no `paths:` filter, and there is no `pr-run-paths` knob

**Question.** When `pr-run-mode != "skip"`, does cargo-dist emit a `paths:` filter on the `pull_request:` trigger, or does the workflow fire on every PR?

**Evidence.** From [`cargo-dist/templates/ci/github/release.yml.j2:65-68`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/templates/ci/github/release.yml.j2):

```jinja
on:
  {{%- if pr_run_mode != "skip" %}}
  pull_request:
  {{%- endif %}}
```

That's the entire conditional. The trigger is a bare `pull_request:` with no `paths:`, `branches:`, or any other scoping. Searching the full 679-line template (`grep -n "pr-run-paths\|pr_run_paths"`) returns zero hits — there is no config knob to scope the PR trigger. Path filtering on `release.yml` PR triggers is something the user adds by hand-editing the generated file (which requires `allow-dirty = ["ci"]`).

Ground-truth comparison:

- **`timcogan/perspecta`**: `dist-workspace.toml` sets `cargo-dist-version = "0.30.4"`, `allow-dirty = ["ci"]`, and **does not set `pr-run-mode`** (so it defaults to `plan`). Their `release.yml:9-19` has `pull_request:` _unfiltered_ on line 10, while the `paths:` filter (`Cargo.toml`, `dist-workspace.toml`, `.github/workflows/release.yml`) lives on the `push: branches: [main, master]` block underneath. The path filter is hand-added under `allow-dirty` and **only scopes the push trigger, not the PR trigger.** Round 1's table entry implying perspecta filters the PR trigger by paths was incorrect; their PR trigger is actually as broad as the template emits.
- **`axodotdev/cargo-dist`**: `pr-run-mode = "plan"`, `release.yml:41-45` is `on: pull_request: \n push: tags: …` — also unfiltered.

**Answer.** No paths filter is generated. The template emits a bare `pull_request:` trigger that fires on every PR. There is no `pr-run-paths` / `pull-request-paths` / `triggers.paths` config field. Scoping the PR trigger to release-infra files is strictly a hand-edit operation, which means it lives under `allow-dirty = ["ci"]`.

### 2. `dist init` skips files listed in `allow-dirty` entirely — no merge, no overwrite

**Question.** With `allow-dirty = ["ci"]`, does regen (a) skip the file, (b) overwrite-with-warning, (c) 3-way merge, or (d) overwrite-and-blame-the-user?

**Evidence.** [`cargo-dist/src/config/mod.rs:872-887`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/src/config/mod.rs) defines the predicate:

```rust
pub enum DirtyMode {
    AllowList(Vec<GenerateMode>),
    AllowAll,
}

impl DirtyMode {
    /// Do we need to run this Generate Mode
    pub fn should_run(&self, mode: GenerateMode) -> bool {
        match self {
            DirtyMode::AllowAll => false,
            DirtyMode::AllowList(list) => !list.contains(&mode),
        }
    }
}
```

`should_run` returns `false` when the mode is in the allow-list. The generation loop in [`cargo-dist/src/lib.rs:875-902`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/src/lib.rs) gates writes on it:

```rust
for &mode in modes {
    if dist.allow_dirty.should_run(mode) {
        match mode {
            GenerateMode::Ci => {
                let CiInfo { github } = &dist.ci;
                if let Some(github) = github {
                    if args.check {
                        github.check(dist)?;
                    } else {
                        github.write_to_disk(dist)?;
                    }
                }
            }
            GenerateMode::Msi => { /* … */ }
        }
    }
}
```

When `mode == GenerateMode::Ci` is in the allow-list, `should_run` returns `false`, the entire `if` body is skipped, and `write_to_disk` is never called. There's no merge, no warning, no diff comparison — just an early-exit on the iteration. `check_integrity`'s drift check (the `args.check` branch) is also skipped, which is why the cargo-dist book frames `allow-dirty` as "skip checking whether the specified configuration files are up to date" (matching the comment string at [`init.rs:1399`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/src/init.rs)).

Issue [#178 ("generated ci desyncs too easily")](https://github.com/axodotdev/cargo-dist/issues/178) and [#909 ("CI: Support configuration of CI permissions (without `allow-dirty`)")](https://github.com/axodotdev/cargo-dist/issues/909) corroborate the framing. #909's reporter wrote _"it 'feels bad' to turn on allow-dirty"_ precisely because it severs all template updates — there is no halfway state where regen merges new template features into the user's hand-edited file.

**Answer.** Semantics (a) — skip entirely. `dist init` regen does not touch `release.yml` while `ci` is in `allow-dirty`. Hand-edits survive every regen, but so does any staleness: template fixes, new partials, security updates to pinned action SHAs, and bug fixes to the Jinja macros all stop reaching `release.yml`. To pick up template changes, the only path is to remove `ci` from `allow-dirty`, run `dist init`, re-apply the hand-edits, and put `ci` back. The lsm-9ns work is safe across cargo-dist version bumps as long as `allow-dirty = ["ci"]` stays — at the cost of a manual diff-and-port step on each cargo-dist upgrade.

### 3. The Attest step has no fork-PR guard; `pr-run-mode = "upload"` would fail on fork PRs

**Question.** Under `pr-run-mode = "upload"`, does cargo-dist's generated workflow guard the `actions/attest-build-provenance` step against fork PRs (where `id-token: write` and `attestations: write` are clamped to read)?

**Evidence.** The build-local-artifacts gate at [`release.yml.j2:181-183`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/templates/ci/github/release.yml.j2):

```jinja
if: ${{ fromJson(needs.plan.outputs.val).ci.github.artifacts_matrix.include != null
    && (needs.plan.outputs.publishing == 'true'
        || fromJson(needs.plan.outputs.val).ci.github.pr_run_mode == 'upload')
{{%- if dispatch_releases %}} || inputs.tag == 'dry-run' {{%- endif %}}
```

No `github.event.pull_request.head.repo.full_name == github.repository` term, no `github.event.pull_request.head.repo.fork` check. The job runs on every PR when `pr_run_mode == 'upload'`, fork or not.

The Attest step itself at [`release.yml.j2:213-328`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/templates/ci/github/release.yml.j2):

```jinja
{{%- if github_attestations is defined and github_attestations and github_attestations_phase == "build-local-artifacts" %}}
permissions:
  "attestations": "write"
  "contents": "read"
  "id-token": "write"
{{%- endif %}}
…
{{%- if github_attestations is defined and github_attestations and github_attestations_phase == "build-local-artifacts" %}}
- name: Attest
  uses: {{{actions["actions/attest-build-provenance"] | safe }}}
  with:
    subject-path: "target/distrib/*${{ join(matrix.targets, ', ') }}*"
{{%- endif %}}
```

The only conditional is the `github_attestations` config flag — there's no `if:` at the step level keying on event type or fork ownership. cargo-dist's own [`release.yml:115-154`](https://github.com/axodotdev/cargo-dist/blob/main/.github/workflows/release.yml) renders the same — `permissions: id-token: write` declared unconditionally on the job, Attest step with no `if:`. cargo-dist itself doesn't trip on this because they run `pr-run-mode = "plan"`, so the build-local-artifacts job's `if:` evaluates false on PRs and the Attest step never executes. Under `upload`, the gate flips and the step runs unconditionally.

GitHub's [token-permission docs](https://docs.github.com/en/actions/security-guides/automatic-token-authentication#permissions-for-the-github_token) confirm fork PRs from public repos receive a read-only `GITHUB_TOKEN` regardless of workflow-declared `permissions:`, so `id-token: write` and `attestations: write` are silently clamped. `actions/attest-build-provenance@v3` requires both, so the step would fail on a fork PR.

I did not find a cargo-dist issue specifically about Attest + fork PRs (`gh search issues "fork pull request attestation"` and "`fork PR pr-run-mode`" both returned zero hits). The combination is undocumented and unhandled in the current template.

**Answer.** No fork-PR guard exists. Under `pr-run-mode = "upload"` with `github-attestations = true`, fork PRs would run `build-local-artifacts`, hit the Attest step, and fail with a permission error. Linesmith's `release.yml` does enable attestations (current `github-attestations` setting in `dist-workspace.toml` is on per the lsm-9ns commit context). Mitigations would be hand-edits — either an `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository` guard on the Attest step, or `pull_request_target` (which carries its own injection-attack risk and is deliberately avoided across the surveyed corpus). Either route adds to the `allow-dirty = ["ci"]` maintenance burden documented in §2.

## Addendum: release-plz vs Knope for per-package versioning (2026-05-23)

The Rounds 1-3 above focused on the **PR-validation question** for the cargo-dist `release.yml` workflow (the trigger surface for binary builds) and drove [ADR-0017](../adrs/0017-release-workflow-pr-validation.md). A separate question — **which tool drives the version-bump + CHANGELOG + crates.io publish side of the pipeline** — surfaced in the v0.2.0 release cycle when release-plz failed to update internal dep-pin version strings at the major-bump boundary. This addendum captures the comparison that drove [ADR-0027](../adrs/0027-knope-for-release-automation.md).

### The failure mode

`feat(core)!: split tool normalizers` (commit 3c4c5ab) bumped `linesmith-core` from 0.1.3 → 0.2.0. Per ADR-0019 (`linesmith-core` published as scaffolding), `linesmith` (the binary) pins `linesmith-core` per-crate rather than via `[workspace.dependencies]`: `linesmith-core = { version = "0.1.3", path = "../linesmith-core" }`. release-plz computed the bump correctly and rewrote `crates/linesmith-core/Cargo.toml`'s `version` field, but **did not** rewrite the pinned version string in `crates/linesmith/Cargo.toml`. cargo's caret-version semantics under `0.x` rules then rejected the workspace: `^0.1.3` excludes `0.2.0` (different "major" series), and the workspace failed to resolve.

The workaround that shipped (commit c1feace, `ci(release-plz): force workspace-version lockstep for major bumps`) added `version.workspace = true` to each crate's `[package]` block — making every crate share one version field. release-plz then bumped that single shared version, dragging `linesmith-plugin` (still at 0.1.x with no breaking change) up to 0.2.0 alongside `linesmith-core`. This defeats ADR-0019's per-package versioning invariant and broadcasts a SemVer-major change to `linesmith-plugin` consumers that didn't actually happen.

### release-plz: known limitation, no fix in flight

release-plz's `update_dependencies` config flag refreshes `Cargo.lock` but **not** pinned version strings in sibling `Cargo.toml` files. Issue [release-plz/release-plz#2199](https://github.com/release-plz/release-plz/issues/2199) tracks the gap; the upstream maintainer's position is that the cross-manifest rewrite is out of scope. The `release_commits` allowlist (currently `^(feat|fix|perf|refactor)` in linesmith's `release-plz.toml`) controls which commit types trigger releases, but doesn't address the dep-pin problem.

No fork of release-plz carrying a local patch was found in the surveyed mature Rust workspaces (`tokio`, `serde`, `clap`, `ratatui`, `cargo-dist`, `uv`). The workaround in production is universally either (a) `version.workspace = true` lockstep, or (b) avoid `[package] version` pins on internal deps (declare via `[workspace.dependencies]` so a single bump cascades). Option (b) doesn't fit linesmith's ADR-0019 posture (linesmith-core and linesmith-plugin are scaffolding crates with per-package version semantics that ADR-0019 explicitly preserves).

### Knope: the `dependency` field handles it natively

Knope's `[packages.<name>] versioned_files` accepts entries shaped like `{ path = "consumer/Cargo.toml", dependency = "consumer-name" }`. Each such entry tells Knope: "when this package's version bumps, rewrite the version pin string in this consumer's manifest, searching the consumer's `[dependencies]` / `[dev-dependencies]` / `[workspace.dependencies]` tables for an entry matching this package name." The `convert-to-monorepo` recipe in Knope's docs lays out the exact shape for a multi-crate Cargo workspace with internal deps.

The auto-detected config Knope emits for a hypothetical workspace where `something` depends on `something-else` (from Knope's `default-config.mdx`):

```toml
[packages.something-else]
versioned_files = [
    "member2/Cargo.toml",
    "Cargo.lock",
    { path = "Cargo.toml", dependency = "something-else" },
    { path = "member1/Cargo.toml", dependency = "something-else" },
]
scopes = ["something-else"]
```

The `{ path = "member1/Cargo.toml", dependency = "something-else" }` entry is exactly the cross-manifest dep-pin rewrite release-plz lacks.

### Other tools surveyed

- **`cargo-smart-release`** — gitoxide's release tool, mature, conventional-commits-aware. Does not handle cross-manifest dep-pin rewrites by name; same gap as release-plz. No PR-based release-preview UX.
- **`cargo-release`** — direct, dispatch-driven. Same gap. Plays well with cargo-dist (Knope's own pipeline uses cargo-release for the `cargo publish` step), but doesn't fix the dep-pin issue.
- **`cargo-workspaces`** — Lerna-style workspace versioning for Cargo. Does support cascading internal dep updates, but the project has been less actively maintained than Knope (last 1.0 release 2024-09). No PR-based workflow.

### Decision matrix

| Concern                                  | release-plz                          | Knope                                                            | cargo-smart-release | cargo-workspaces   |
| ---------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- | ------------------- | ------------------ |
| Per-package versioning                   | Yes (with caveats above)             | Yes (native)                                                     | Yes                 | Yes                |
| Cross-manifest dep-pin updates by name   | **No** (#2199 unfixed)               | **Yes** (`dependency` field)                                     | No                  | Yes                |
| PR-based release preview                 | Yes                                  | Yes (workflow recipe + bot mode)                                 | No (dispatch-only)  | No                 |
| Conventional-commits version computation | Yes                                  | Yes                                                              | Yes                 | Yes                |
| Changeset-file workflow                  | No                                   | Yes (`knope document-change`)                                    | No                  | No                 |
| crates.io publish                        | Yes (built-in `release-plz publish`) | Delegated to `cargo release publish` (skips already-published)   | Yes                 | Yes                |
| Maintainer activity (last release)       | active (multiple per month)          | active (`knope/v0.22.4` 2026-03-21)                              | active              | sporadic           |
| External GitHub App dependency           | No                                   | Optional (`bot.releases = true`)                                 | No                  | No                 |
| Surveyed production users                | many (uv, ratatui, etc.)             | Knope itself (monorepo), a handful of Rust projects on crates.io | gitoxide ecosystem  | cargo-bisect-rustc |

### What this leaves open

- **Knope's GH Release "latest" race during the cargo-dist build window.** Knope's `Release` step creates per-package GitHub Releases on release-PR merge (linesmith-core, linesmith-plugin, linesmith — all three if all bumped). cargo-dist's `release.yml` only fires for `linesmith/v*` tags and marks that release `--latest` after binaries upload (~10 min later). During the build window, GitHub's "latest" pointer briefly points at whichever library release Knope created last. Mitigation: doctor's `parse_three_part_version` strips per-package tag prefixes (this PR), so a transient `linesmith-core/v0.3.0` showing as `/releases/latest` doesn't WARN. Open question: whether to teach Knope to create library releases as drafts (set `assets = "marker"` on each) and have a follow-up workflow promote them, mirroring Knope's own `add_release_assets.yml` pattern. Punted for the initial migration; revisit if the brief race becomes user-visible.

- **Empirical validation of Knope's per-package bump shape at the next major boundary.** ADR-0027 asserts Knope's `dependency` field structurally prevents the v0.2.0 failure mode. Confirmation requires a real release cycle with a breaking change to `linesmith-core` (or `linesmith-plugin`) flowing through. Tracked in ADR-0027 §Confirmation.

- **Changeset-file adoption.** Conventional commits remain the primary release-impact signal; changesets are a supplement. Whether contributors actually reach for `knope document-change` when commit subjects are insufficient depends on the eventual contributor base — currently single-maintainer.
