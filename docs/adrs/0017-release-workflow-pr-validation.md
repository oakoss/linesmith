# Use a hand-edited path-filtered pull_request trigger for release-workflow validation

- Status: accepted
- Date: 2026-04-28
- Deciders: Jace

## Context and Problem Statement

[ADR-0007](0007-cargo-dist-distribution.md) chose `cargo-dist` for multi-target release distribution. The autogenerated `release.yml` runs on tag push (real release) and was extended in [bead lsm-9ns] with a `workflow_dispatch` dry-run path so maintainers can validate the 7-target build matrix without cutting a real tag. That covers manual validation but doesn't catch the case where a PR modifies cargo-dist-related release-infra files (`release.yml`, `dist-workspace.toml`, `Cargo.toml`) and breaks something only the build matrix would surface — the v0.1.1 first-attempt failure (`aarch64-pc-windows-msvc` cross-compile chain breaking) is the canonical example. How should release-infra PRs be validated automatically before merge?

## Decision Drivers

- Catch the historical failure class (cross-compile / target-list bugs) before tag-push, not after
- Don't fire the 7-target build matrix on every PR — only on PRs that touch release-infra
- Don't rely on maintainer memory to remember to dispatch the dry-run before merging
- Stay aligned with cargo-dist's autogen model where possible; minimize hand-edit surface
- Public-repo Actions minutes are free, but the GitHub Free plan caps **20 concurrent jobs account-wide**. A 7-target fan-out claims 7 of those slots per run.
- Honor the existing `allow-dirty = ["ci"]` discipline so cargo-dist version bumps don't silently revert release-infra hand-edits

## Considered Options

- **`pr-run-mode = "upload"` (cargo-dist's documented PR validation path)**: flip a one-line config change in `dist-workspace.toml` and let cargo-dist regenerate `release.yml` with a `pull_request:` trigger
- **`pr-run-mode = "plan"`**: flip to the lighter validation mode that runs `dist plan` only (config syntax + CI YAML drift)
- **`workflow_run` trigger** chained after ci.yml: release.yml fires only after ci.yml passes
- **Reusable workflow (`workflow_call`)**: extract ci.yml's checks into a callable reusable workflow; release.yml `needs:` it
- **wait-on-check-action** (3rd-party): release.yml polls GitHub's check API for ci.yml's status before starting the build matrix
- **Hand-edited path-filtered `pull_request:` trigger**: keep `pr-run-mode = "skip"`; manually add a `pull_request:` trigger with a `paths:` filter to release.yml, plus a fork-PR `Attest` guard
- **Status quo**: rely on `workflow_dispatch` (manual) + branch protection (gates merge but doesn't validate)

## Decision Outcome

Chosen option: **hand-edited path-filtered `pull_request:` trigger**, because three rounds of [release-workflow research](../research/release-workflow-patterns.md) established that the alternatives either don't catch the failure class we care about (`plan`), can't be path-filtered natively (`upload` fires on every PR with no `paths:` knob), have security caveats that defeat the purpose (`workflow_run` uses the default-branch's workflow definition, so PRs modifying release.yml don't exercise the modified version), or require heavyweight refactors that fight cargo-dist's autogen model (reusable workflows, wait-on-check-action). cargo-dist's own template emits a bare `pull_request:` under `pr-run-mode = "upload"`; getting path-filtering, fork-PR Attest guarding, or a `compute-tag` PR-event case all require hand-edits regardless. If we're hand-editing anyway, the explicit `pr-run-mode = "skip"` + path-filtered hand-edit is cleaner than overriding an autogen'd trigger surface.

Implementation shape (specs/release-process.md will document the contract):

- `release.yml`: add `pull_request:` to `on:` with `paths:` filter for `release.yml`, `dist-workspace.toml`, `Cargo.toml`, `crates/*/Cargo.toml`, `Cargo.lock`. The path list is deliberately narrow — only files whose changes can affect what `release.yml` itself executes. `release-plz.yml` and `release-plz.toml` are excluded because triggering `release.yml` on those would burn 7 runner slots without exercising any release-plz code path (release.yml's matrix runs cargo-dist, not release-plz). `Cargo.lock` is included because lockfile changes (cargo-update, release-plz's auto-bumps, dependabot) shift the exact dependency graph that gets cross-compiled, and transitive-dep build-script changes are a common entry point for target-specific breakage that wouldn't surface until tag-push otherwise.
- Extend `compute-tag` step's `case` to handle `pull_request` events, synthesizing the ephemeral tag from `github.event.pull_request.head.sha` (the PR head, not the merge SHA that `${GITHUB_SHA}` provides on PR events).
- Widen `build-local-artifacts` `if:` gate to admit `event_name == 'pull_request'`.
- Widen `retention-days` ternaries so PR builds get 7-day retention.
- Add a fork-PR guard to the `Attest` step: `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository`. Fork PRs hit this step and fail without it because GitHub clamps `id-token: write` to read on fork-PR contexts.
- Add `concurrency:` block with `cancel-in-progress: true` for `pull_request` events so superseded PR pushes cancel their predecessor's 7-target build.
- `dist-workspace.toml`: keep `pr-run-mode = "skip"`. The hand-edited trigger is what fires; cargo-dist's mode controls a different, conflicting trigger surface that we don't want to invoke.

**Validation surface caveats.** Triggering `release.yml` on a `dist-workspace.toml` change exercises only the keys cargo-dist reads at runtime (target list, build profile, attestations toggle, etc.). Keys that affect generated CI shape — `[dist.github-action-commits]`, runner customizations, the trigger surface itself — only take effect after `dist init` regen rewrites `release.yml`. Under `allow-dirty = ["ci"]` (Round 3 §2), regen skips the file entirely, so a CI-shape change to `dist-workspace.toml` won't actually exercise until `release.yml` is regenerated and committed in the same PR. This filter validates the runtime config; the regen-driven keys remain a maintainer-discipline concern.

**Out of scope (separate gaps).** `release-plz.toml` and `release-plz.yml` changes get no PR-time validation from this ADR's contract. release-plz has no check-only subcommand (Round 2 §2), and triggering `release.yml` on those files would be false coverage. File a follow-up bead to either invent a custom validator (e.g., `release-plz update` against a scratch checkout in ci.yml with `git diff --exit-code` semantics) or accept the gap.

### Consequences

- Good, because release-infra PRs surface cross-compile bugs pre-merge, on the same SHA that will eventually be merged
- Good, because non-release-infra PRs (Rust source, README, segment additions, etc.) don't fire the 7-target build matrix — concurrency budget preserved for release work
- Good, because the path-filtered trigger composes cleanly with the existing `workflow_dispatch` from lsm-9ns; both routes share the same `compute-tag` and gating logic
- Good, because fork-PR Attest now fails gracefully instead of cryptically
- Bad, because hand-edits to release.yml accumulate; each cargo-dist version bump (currently 0.31; future bumps inevitable) requires manually un-allow-dirty → regen → re-apply our edits → re-allow. Round-3 research confirmed `dist init` semantics under `allow-dirty = ["ci"]` is "skip the file entirely," so template fixes don't reach the file until that manual cycle runs
- Bad, because the `paths:` filter is best-effort. A bug class we haven't catalogued (e.g., a Rust-source change that triggers a cross-compile failure only at link time) will sneak through. Mitigation: `workflow_dispatch` remains the maintainer escape hatch
- Bad, because release-plz.toml and release-plz.yml changes don't get a corresponding gate. The path filter deliberately excludes them to avoid false coverage (triggering release.yml validates cargo-dist code paths, not release-plz). Acknowledged gap; tracked separately
- Bad, because `dist-workspace.toml` changes that affect generated CI shape (e.g., `[dist.github-action-commits]`) only validate when `release.yml` is regenerated in the same PR — under `allow-dirty = ["ci"]` regen is skipped, so the trigger fires but exercises the old workflow. Maintainer-discipline concern; documented in the validation-surface caveat
- Neutral, because the same hand-edit pattern (path-filtered `pull_request:` + `Attest` fork guard) is now established for any future release-adjacent workflow we add

### Confirmation

This decision is confirmed when:

1. A test PR touching `dist-workspace.toml` (a runtime-read key, e.g., `targets`) triggers release.yml automatically and runs the full 7-target build matrix.
2. A test PR touching only `Cargo.lock` (e.g., a release-plz auto-bump or `cargo update`) triggers release.yml automatically — the lockfile-shifts-dependency-graph case the path filter is designed to catch.
3. A test PR touching only Rust source does NOT trigger release.yml.
4. A test PR touching only `release-plz.toml` does NOT trigger release.yml (no false-coverage from the cargo-dist matrix).
5. A simulated fork PR (or a check-run with explicit fork-context simulation) skips the Attest step gracefully without failing the workflow.
6. cargo-dist 0.32+ regen via the documented un-allow-dirty cycle preserves the hand-edits when re-applied.

Revisit if:

- cargo-dist adds native `pr-run-paths` support (would let us flip to `pr-run-mode = "upload"` and drop hand-edits)
- The 20-slot concurrency cap becomes a real constraint (project grows past one maintainer with multiple parallel release-infra PRs)
- Branch-protection / required-checks evolves to include workflow-run dependency expressions natively

## Pros and Cons of the Options

### `pr-run-mode = "upload"`

- Good: cargo-dist's documented setting for PR-time build validation
- Good: changes to dist-workspace.toml are picked up by regen; less drift over time
- Bad: emits a bare `pull_request:` (fires on every PR including unrelated ones) — burns 7 of 20 concurrent slots per non-release-infra PR
- Bad: doesn't include a fork-PR Attest guard; we'd hand-edit anyway
- Bad: needs hand-edited `compute-tag` PR-event case for head-SHA correlation
- Bad: net hand-edit count is the same as the chosen option, just spread across two locations (toml + yml)

### `pr-run-mode = "plan"`

- Good: cheapest option — `dist plan` is config-validation only, ~30 sec on 1 runner
- Bad: doesn't catch build-time bugs. `dist plan` never invokes `cargo build`, `rustup`, `xwin`, or `zigbuild` — it's `dist manifest` plus a CI-YAML integrity check. The v0.1.1 cross-compile failure would have passed `plan` cleanly. Documented in cargo-dist's own [troubleshooting](https://opensource.axo.dev/cargo-dist/book/cargo-dist/usage.html) which recommends `upload` for exactly this class of bug

### `workflow_run` trigger

- Good: native GitHub Actions feature; no 3rd-party dependency
- Bad: uses the default-branch workflow definition (security policy), so PRs modifying release.yml itself wouldn't exercise the modified version. Defeats the purpose of validating release-workflow changes

### Reusable workflow (`workflow_call`)

- Good: canonical GitHub Actions pattern for "test before release"; uv uses it for `check-release.yml`
- Bad: requires extracting ci.yml's checks into a separate callable workflow file
- Bad: the resulting needs-chain would span hand-edited and autogenerated files (cargo-dist regenerates release.yml whole)

### wait-on-check-action

- Good: stays inside release.yml, no cross-workflow refactor
- Bad: 3rd-party action with API-polling latency (~30 sec setup per matrix leg)
- Bad: no surveyed Rust release pipeline uses this pattern; non-idiomatic in the ecosystem

### Status quo (workflow_dispatch only)

- Good: zero PR-time concurrency cost
- Good: no additional hand-edits beyond lsm-9ns
- Bad: relies on maintainer memory; release-infra PRs can land without validation if no one remembers to dispatch
